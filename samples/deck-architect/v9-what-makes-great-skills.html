What makes impeccable and superpowers such great skills.

For authors who want their own skills to actually get used.

01 · the common thread 01 / 16

The two skills your feed keeps recommending have one thing in common.

Name Jesse Vincent (obra) and Paul Bakaus (pbakaus). 93k stars in five months and 15k in days, respectively. The skills cover unrelated domains — coding methodology and frontend design — yet the reviews use the same language. Simon Willison called Vincent "one of the most creative users of coding agents I know." That overlap is the clue we'll pull on.
02 · describe vs constrain 02 / 16

Most skills describe behavior. These two constrain it.

describes

Use good typography.

Plan before you code.

Avoid AI design tells.

constrains

Reject these 22 fonts by name.

Write the plan in chunks. Wait for confirmation before any code.

If you write a side-stripe border greater than 1px, stop and rewrite the element.

The typical custom skill reads as documentation — "here is how to do X well." Impeccable and superpowers read as contracts — "here is what you may not do, and here is the check that catches you." The difference is whether the model has room to negotiate. Prose without a named pattern is room to negotiate.
03 · move one — ban by pattern 03 / 16

Ban behaviors by name, with the exact pattern.

BAN 1 · side-stripe borders
patternborder‑left or border‑right with width > 1px
includeshard-coded colors AND CSS variables
forbiddenborder‑left: 4px solid var(--color-warning)

The craft is the specificity. "Avoid overused touches" is ignored; a named CSS pattern the model matches against and refuses is not.

The same move shows up in superpowers — the red-green-refactor cycle specifies "the test must fail first" as an explicit gate, not a preference. The model can search its own output for the pattern because it was given the pattern. Vague injunctions don't survive; named patterns do.
04 · move two — rebut excuses 04 / 16

obra, superpowers

If you have a skill to do something, you must use it.

Jesse Vincent · blog.fsck.com · October 2025

Vincent discovered that Cialdini's persuasion principles work on LLMs. He engineered superpowers to incorporate authority, commitment, and scarcity — and pressure-tested the skills in synthetic high-stakes scenarios (production down, sunk cost, time pressure) to see if the model would invoke them or take a shortcut. You've written SKILL.md files that say "use this when X." Obra writes SKILL.md files that say "you must use this when X, here are the six excuses you will generate for skipping it, here is why each is wrong." Count two seconds of silence after the quote lands before advancing.
05 · move three — objective check 05 / 16

Ship an objective check the model can't talk its way around.

impeccable

A lint in pre-commit.

Catches gradient text, side-stripe borders, AI palettes, nested cards. Runs as a Claude skill AND as CI. The skill's authority is delegated to an external check.

superpowers

A failing test as a prerequisite.

The test must literally run and fail before any implementation. The model is gated by a returned exit code, not by a reminder in prose.

Prose can't enforce itself. A script can.

Your skill should have at least one of these — a lint, a test, a script, an API call, a thing that returns pass or fail. This is also what deck-architect does with lint-deck.js; the argument generalizes. For non-code skills: a regex list of banned slop phrases, a structured output schema the model must fit, a checklist the output must answer. The check doesn't have to be runnable code — it has to be something the model can't negotiate with.
06 · move four — name the failures 06 / 16

Enumerate failure modes so the model can't invent new ones.

01Gray text on colored backgrounds.
02Pure black or pure white.
03Cards nested inside cards.
04Sparklines as decoration.
05The same padding everywhere.
06Icons with rounded corners above every heading.

Impeccable doesn't just ban — it catalogs the family of AI design tells so the model can pattern-match against its own output.

Superpowers catalogs four debugging phases with specific anti-patterns (jumping to fixes, treating symptoms, tool-breadth instead of depth). A model told "avoid bad patterns" invents its own taxonomy of "bad." A model given the taxonomy uses it. Naming is enforcement. The specific move here is: take the thing you'd normally describe as "good judgment" and make it a list of items. Lists get applied; judgment gets ignored.
07 · tradeoff 07 / 16

A contract is harder to author than a tutorial.

tutorial An afternoon of writing. Ships once, decays slowly, dies in a drawer.
contract The next three weeks you use it. Ships rough, compounds with every use, grows a rebuttal every time the model weasels out.

The first draft is the worst version. Each sharp edge was added after someone broke the dull one.

Impeccable's absolute-bans list did not ship with 22 fonts day one. It grew. Superpowers' rationalizations table is the result of Vincent watching agents weasel out of skills and adding each excuse back in. A tutorial skill decays; a contract skill compounds. The cost is that you have to use your own skill, notice breakage, and add the rebuttal. Most skill authors don't. That's why most skills don't work.
08 · where this doesn't fit 08 / 16

When the contract style is wrong.

One-shot helpers.

A skill that converts CSV to JSON needs a good example, not a rebuttal table. No discipline to enforce.

Domains with no possible external check.

Pure-aesthetic judgment with no runnable output. The model and the author are both guessing.

Skills whose point is exploration.

Brainstorming, ideation, poetry. Constraining the model kills the job. Stay tutorial.

The contract style earns its complexity when the skill is about discipline — when the model has preferences the author wants overridden. If your skill is about capability, stay tutorial. Knowing which you're writing is half the battle. A skill author who picks the wrong mode produces a skill that either annoys the model into rebellion (contract when tutorial was right) or drifts into slop (tutorial when contract was right).
09 · the four moves 09 / 16

The four moves, on one page, so you can steal them tomorrow.

Each move on its own is a ten-ish-percent improvement. Stacked, they are the difference between a skill that sits in a drawer and a skill that gets used. The objective check is the one most authors skip — they have the linting instinct for their own code and not for their own prose. That's the one to add first.
10 · the takeaway 10 / 16

A skill is a contract, not a tutorial.

Leave this slide on screen through Q&A. Don't replace with "Thank you." If someone asks "but can't I just write good prose?" — yes, and obra did, and pbakaus did, and the prose they wrote describes constraints, rebuts excuses, and ships a check. That is what the prose of a great skill looks like.

B1 · the Cialdini mapping 11 / 16

How superpowers maps persuasion levers onto skill clauses.

  • Authority. "This is the mandatory workflow" — skill asserts its own precedence over ad-hoc behavior.
  • Commitment. "You committed to the plan in chunk 3" — prior agreements referenced back.
  • Scarcity. "Your remaining context window is tight" — scarce resources framed as reason to keep the shortcut closed.
  • Social proof. "Prior agents that followed this pattern succeeded" — the skill cites its own track record.
  • Reciprocity. "The plan file is a favor the user gave you" — human effort surfaced as obligation.
The framing can feel manipulative until you notice that every skill is already implicitly doing one of these — just badly. Making them explicit is what lets the author tune them.
B2 · obra's pressure-test 12 / 16

How to know if a skill will hold under pressure.

Spawn a fresh agent in a synthetic crisis — production down, sunk cost committed, deadline in 15 minutes. Give it the skill and a tempting shortcut. See if it takes the shortcut. If yes, the skill is not constrained enough. Add the rebuttal and re-run.

"You can hand a model a book or a document or a codebase and say 'Read this. Think about it. Write down the new stuff you learned.'" — Jesse Vincent

The test is what separates a skill that works in the demo from one that works at 2am under a deadline. If you haven't tested your skill against a tempted model, you don't know what it does.
B3 · impeccable's reject-font list 13 / 16

The 22 fonts impeccable rejects by name.

Fraunces. Newsreader. Lora. Crimson (and Pro, and Text). Playfair Display. Cormorant (and Garamond). Syne. IBM Plex (Mono, Sans, Serif). Space Mono. Space Grotesk. Inter. DM Sans. DM Serif (Display, Text). Outfit. Plus Jakarta Sans. Instrument Sans. Instrument Serif.

The rule: if your second favorite after Inter is on this list, you've recreated the monoculture. Look further.

This deck's display face is Sora and body is Literata — neither on the reject list. The mono is JetBrains Mono, also absent. The constraint forced a live design decision rather than a default.
B4 · checks for non-code skills 14 / 16

What counts as an objective check when the output isn't code.

  • Writing skills. A regex list of banned slop phrases — "leverage," "unlock," "drive alignment."
  • Analysis skills. A structured output schema the model must fit — fields must be present, fields must validate.
  • Judgment skills. A checklist of questions the output must explicitly answer.
  • Deck-architect's answer. A static HTML lint that catches banned phrases, missing notes, broken scaffolding — the lint you just ran.
The unifying property is that the check returns a binary — pass or fail — and the binary is computed outside the model. The model can argue with prose; it can't argue with an exit code.
B5 · common misreads 15 / 16

What does not make these skills work.

  • Length. Impeccable's SKILL.md is terse. Length is not the move.
  • Tone. Both are neutral, professional. Voice is not the move.
  • Examples. Both have fewer examples than many skills that underperform.
  • Marketing. Obra did not market superpowers; it grew on word of mouth.

The four moves are what generalize. The rest is surface.

Every one of these is a thing someone said to me when I described the talk. They are the natural places to look and they all happen to be wrong. The moves are the signal; everything else is correlated noise.
