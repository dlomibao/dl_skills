02 · The reframe02 / 16
Both skills share the same hidden architecture

Discipline-enforcement systems, not capability-addition systems.

What users think these skills do

  • Adds TDD to Claude
  • Adds a design language
  • Drops in a "better" prompt
  • Makes output look nicer

What they actually do

  • Enforces TDD by anticipating skip rationalizations
  • Enforces design by banning defaults the model reaches for
  • Replaces the model's defaults with the author's defaults
  • Treats the model's trained reflexes as the adversary

"If you have a skill to do something, you must use it."— obra, superpowers

04 · Lesson 204 / 16
Lesson 02 of 05

Anticipate the model's rationalizations. Pre-empt them inline.

Under pressure the model finds loopholes. The list of loopholes is nearly identical across users — surface them and rebut them by name.

If you think……do this instead
"I need more context before running the skill." Skill check comes BEFORE clarifying questions.
"This task is simple enough — I can skip the plan." The skill was written for cases that feel simple. Especially then.
"The tests are already passing, so TDD isn't needed." TDD is not a safety net. Write the failing test first, always.
"I'll ask the user if they want the skill." Don't outsource the decision. If the trigger matches, invoke.

05 · Lesson 305 / 16
Lesson 03 of 05

Add objective enforcement. Not vibes.

Instructions decay under model variance. Programmatic checks don't. Your skill probably has zero verification today.

superpowers · pressure test

Skills are tested by being invoked under stress

A subagent simulates a typical user request. If the skill doesn't fire when it should, the skill is wrong — not the test. Trigger reliability is the metric.

Evidence: mejba.me controlled test found a 14% token reduction with superpowers. Honest caveat — the "40% quality" headline was overstated for simple tasks.

06 · Lesson 406 / 16
Lesson 04 of 05

Decompose by failure mode — not by topic.

Topic decomposition ("frontend skill," "backend skill") creates skills too broad to trigger reliably. Failure-mode decomposition fires exactly when needed.

Wrong way · by topic

One big "design" skill that says: do everything well.

frontend backend docs testing

Broad triggers misfire. Vague guidance doesn't enforce anything.

Right way · by failure mode

18 commands in impeccable, each targeting one specific model failure.

/audit /distill /colorize /harden /quieter
brainstorming writing-plans debugging code-review

Start with one failure mode per skill. Decompose only when you observe the same skill firing for genuinely different failures.

08 · What it costs08 / 16

What you're giving up.

Discipline-enforcement skills are longer, more opinionated, and harder to write than encouraging ones. Name the tradeoff honestly.

COST 01

Bigger SKILL.md

A 12-row rationalizations table doubles your file size. Higher token cost per session — this is real, not hypothetical.

COST 02

Opinionated skills fight edge cases

The ban that usually helps sometimes blocks a legitimate choice. You'll ship corrections for a week.

COST 03

You need the expertise

Anti-pattern lists require you to actually know the anti-patterns. There's no shortcut around having taste.

Smallest version still helps: one banned phrase + one rationalization rebuttal beats a vague encouraging skill.

09 · When not to09 / 16

When not to do this — and how to roll back.

01
Don't enforce on skills with fewer than 5 invocations of evidence. You'll over-fit to one accident.
02
Don't ban behaviors you can't articulate the replacement for. "Don't be generic" with no direction just confuses the model.
03
If the discipline-enforcement skill conflicts with explicit user instructions, the user wins. This is in superpowers' own priority list.
Rollback path
$ cp SKILL.md SKILL.md.v1 $ # ship the new version $ # track invocations for 3 days $ # if count drops > 30%, revert $ mv SKILL.md.v1 SKILL.md

Leading indicator beats a weekly check. If you notice reliability drop on day 3, you haven't lost a week of correct invocations.

Backup · B4 · depth L314 / 16

Why does the language sound so authoritarian?

Triggered by: "Doesn't 'EXTREMELY-IMPORTANT' backfire?"

obra's own framing: Cialdini's principles, applied to the model, not to the user.

  • Authority · rules stated as from a system, not a suggestion
  • Commitment · "you MUST" binds the next step in the session
  • Scarcity · "before anything else" — no budget for deferral
  • Consistency · repeated bans reinforce the one from three slides ago

"These aren't aesthetic choices. They are testing-derived. Each line earned its caps through a failure I watched happen."— obra · blog.fsck.com/2025/10/09

Caveat: authoritarian phrasing can collide with user instructions. superpowers resolves this with an explicit priority list — user instructions win.

Backup · B5 · depth L315 / 16

How impeccable's CLI scanner works.

Triggered by: "How would I build something like that?"

The scanner reads static HTML/CSS. No AI required. Runs in CI, runs pre-commit, runs in the hands of a reviewer who doesn't trust the model.

  • Parse the DOM; extract used fonts, colors, spacing tokens
  • Compare against the ban-lists from the skill
  • Run contrast ratios through an OKLCH-aware calculator
  • Flag heading-level skips, orphaned cards-in-cards, gradient-text
  • Output: machine-readable JSON + human-readable report
$ impeccable verify ./dist reading ./dist/index.html parsing 24 CSS rules running 24 detection rules ✕ typography.banned-font font-family: Inter (line 42) ✕ color.pure-black color: #000000 (line 87) ✕ layout.card-in-card .card .card nested (line 104) ✓ contrast.aa-pass 17/17 text-bg pairs ✓ heading.no-skip h1 → h2 → h3 → 3 violations · 2 auto-fixable · see ./impeccable-report.json
