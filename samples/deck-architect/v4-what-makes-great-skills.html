02 · the reframe02 / 16

Both skills are enforcement systems dressed as capability skills.

What people install them for

  • Better typography
  • A TDD workflow
  • Clean design output
  • A checklist you can hand to the model

What they actually do

  • Ban the eleven fonts Claude defaults to
  • Pre-empt the fourteen excuses Claude uses to skip TDD
  • Refuse the design patterns before generation
  • Encode the rules so a node script can enforce them
This is the STAR line. Quote pbakaus on generic-template convergence; quote obra on "if you have a skill to do something, you must use it." Both authors explicitly name the model's own defaults as the adversary. The surface features users install for are downstream of that framing. If the audience only remembers one slide, this is the one they will paraphrase.

"Use good fonts" activates nothing — the model's prior for "good font" is Inter. "Do not use Inter, DM Sans, Plus Jakarta, Instrument Serif, Fraunces, Space Grotesk, Newsreader, Lora, Crimson, Outfit, Cormorant" forces a decision. The move generalises outside visuals: this deck was written with deck-architect, which ships a forbidden-phrase list for the same reason. Name the token you want killed; name the replacement. If your skill tells the model to "be careful" or "be thorough," you have written guidance, not a skill.
04 · move 02 · rebut the excuse04 / 16

Rebut the rationalization before the model writes it.

What the model is about to think The rebuttal that fires first
“This case is special.” No exceptions. Tests still run.
“The user is in a hurry.” Speed comes from skipping review, not skipping tests.
“This is a trivial change.” Trivial changes are where silent regressions hide.
“I already understand the problem.” Write the failing test and confirm your understanding.
“One-percent risk is acceptable.” One-percent means you MUST check.

Excerpt of the superpowers Red Flags table. The pattern is the move; the exact list is domain-specific to the skill.

The excuses Claude reaches for under time pressure are uniform across sessions. Observe the ones your own skill provokes once, then write the rebuttal inline. This is the move that separates usable from installed — it is why superpowers feels different from "a good prompt." The rationalization is named before it runs. Ask the room: what excuse does your last-authored skill fail on most? Whoever answers first has their Friday task.
05 · where skills sit05 / 16

Where the two skills sit, compared to what power users typically ship.

Most power-user skills live in the broad-but-soft quadrant — they cover a lot of surface with polite guidance. The shipping move is not to redraw the skill; it is to add teeth. A narrow but sharp skill beats a broad but soft one every time, because the narrow one actually fires. This quadrant is a thinking tool, not a ranking — grading my own two skills here is itself a bias. Invite the room to plot one of their own.
06 · move 03 · run the check06 / 16

Ship a check that runs without Claude. Evidence the audience can verify.

Impeccable ships a node script that audits rendered HTML/CSS for ~24 anti-patterns — no model at runtime. Superpowers ships a subagent pressure-test methodology. The chart is Mejba's paired-session data; the teeth are what the data measures.

The slide earns its bar chart because the argument depends on numbers the audience must see. Instructions drift under model variance. Programmatic checks do not. Mejba's twelve paired sessions show effect concentrated on complex multi-file tasks — which maps exactly to the skill chain on the next slide. Name the n directly if anyone asks — twelve sessions is thin, and the honesty is what buys credibility for everything downstream.
07 · move 04 · split by failure07 / 16

Decompose by failure mode. Then chain the skills.

Topic-decomposition ("a design skill," "a testing skill") creates surfaces too broad to fire reliably. Failure-mode decomposition creates skills that fire exactly when needed. Once each skill is sharp enough to trigger on its own, chain them. Schwartz's review names the chain effect explicitly — no single skill did the work. The fourteen-percent token reduction on the previous slide was concentrated on exactly the complex multi-step tasks where this chain ran end-to-end. Pragmatic threshold: one failure mode per skill until the same skill fires for genuinely different failures.
08 · what you give up08 / 16

What you give up: longer files, sharper edges, real authoring time.

  1. SKILL.md roughly doubles. A ban list and a rebuttal table are real tokens. A twenty-line skill becomes a forty-line skill before you have measured anything.
  2. Opinionated skills fight the user on edges. Enforcement cuts both ways — sometimes the user was right. You need an override path, and you need to actually use it when the override is correct.
  3. The first pass is weak and you have to live with it. You cannot write a ban list for a domain you have not lived in. The skill sharpens only with invocation data; budget for the second version.
The smallest useful version is one banned token plus one rebutted excuse. Twenty authoring minutes, not a weekend. Name the "sounds heavy" instinct directly — the audience is thinking it before you say it. Call out one skill you would not apply these moves to this quarter and why: if the skill has no invocation data yet, you are guessing at the ban list and will ban things you later need.
09 · rollback09 / 16

If this backfires, catch it in 72 hours — not next sprint.

The 72-hour check

  • AKeep the prior SKILL.md as SKILL.md.prev beside the new one. One-line diff is your rollback path.
  • BLog invocation count for 72 hours after the change. A terminal ring-buffer of fired-skill names is enough.
  • CIf invocations drop by more than 30% against the trailing week, triggering regressed — restore, diagnose, retry.

When not to do this

  • No enforcement on skills with fewer than five real invocations — you are guessing.
  • No ban without a specific replacement — half a move is worse than no move.
  • If enforcement consistently fights user intent, the user wins. Every time.
Anticipate the "I will not notice regressions for a week" objection head-on. The 72-hour check is cheap, survives being forgotten, and catches the failure mode of a ban list with no replacement. The 30% drop threshold is a practitioner heuristic, not a controlled number — if someone pushes on it, flag that and be honest. The point is the existence of a pre-committed threshold, not its exact value. Rollback is not a backup slide because this deck asks for a change to a working artefact.
10 · one skill, two moves, Friday10 / 16
A great skill is an enforcement system tuned to Claude's specific failure modes — not an instruction manual for behaviours you wish the model had.
Pick One skill you already own.
Apply Move 01 + Move 02. By Friday.
Check Invocation count, 72 hours, 30% threshold.
The deck succeeds when the audience names a skill. Ask for one aloud before the room moves on — the public commitment is what makes Friday happen. Move 01 + Move 02 are the "if unsure" pair: Move 01 is the cheapest change possible, Move 02 is the check that catches the failure mode of Move 01 (a ban list with no replacement produces the same guidance hole you started with).

B4 · why the tone15 / 16

The “you MUST” language is testing-derived, not stylistic.

Authority, commitment, scarcity — Cialdini's three levers that reliably shift behaviour, applied to a model that will argue its way out of a soft instruction but comply with a hard one. The capital letters are load-bearing. obra — fsck.com, late 2025 (paraphrased)

The uppercase tags (“EXTREMELY-IMPORTANT”) look aesthetic but were arrived at by measuring compliance. Soft versions produced measurably worse adherence. Treat tone decisions as testable.

Answer to the "isn't the authoritarian tone off-putting?" objection. The tone is a feature, not a bug. You can be warm in prose and firm in instructions — the firmness is specifically what gets obeyed. Soft enforcement is indistinguishable from suggestion, which is why it fails silently.
B5 · the CLI inside16 / 16

How Impeccable's auditor is shaped.

Reads rendered HTML and CSS, applies roughly 24 deterministic checks — font family against a reject list, gradient-text detection, border-left width ban, contrast ratios, heading monotonicity, padding rhythm on a 4pt scale. No AI runtime at execution time; a Node script. CI-runnable.

The architectural move is: any skill can ship with a companion verifier. The verifier does not need to understand intent — it only needs to encode the bans. A few hundred lines of deterministic code buys external verification that the skill's instructions are being followed.

$ impeccable audit build/index.html
  ok: no reflex fonts
  ok: no gradient text
  ok: heading monotonicity
FAIL: border-left 4px on .callout
FAIL: card nested inside card (.panel > .panel)
FAIL  build/index.html — 2 check(s) failed
This deck was itself linted by a companion script on the same architectural pattern — regex checks over the rendered HTML, no model in the loop. The payoff is asymmetric: the effort to build is one afternoon; the reliability buy is permanent. If someone asks "can I really do this for my own skill" — yes, and the smallest useful version is a single check for your single most common failure.
