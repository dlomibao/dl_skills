The design moves behind impeccable and superpowers.

For Claude Code authors who already ship their own.

01 · The answer, up front01 / 16

Your skills mostly prescribe behaviour. The best ones proscribe it.

The move is not adding capability. It is closing off the model's default failure paths.

  • Move 01Name the specific anti-pattern.
  • Move 02Rebut the rationalization before the model writes it.
  • Move 03Ship a check that runs without Claude.
  • Move 04Decompose by failure mode, not by topic.
This is the thesis of the talk, stated before defending it. The eight body slides that follow each defend one move with direct evidence from impeccable and superpowers. Slide 8 is the honest-costs slide. Slide 9 is the rollback. Slide 10 is the action. Resist promising a tool tour — the audience is expecting one, and they will pay attention when they don't get one. The two skills everyone is already copying are impeccable and superpowers; name them by name here, in voice, so the cover doesn't have to carry that framing.
02 · The reframe02 / 16

Both skills are enforcement systems dressed as capability skills.

What people install them for

  • impeccable — “better fonts and layout”
  • superpowers — “a TDD and planning workflow”

What they actually do

  • Ban the fonts Claude reflexively picks.
  • Pre-empt the excuses Claude uses to skip TDD.
This is the STAR moment — the thing the audience will quote to a teammate afterward. Quote pbakaus on generic-template convergence: every LLM learned from the same handful of design templates, so the default output is everybody's default output. Quote obra: "If you have a skill to do something, you must use it" — the model's first reflex is to explain why this case is different, and the skill has to shut that down. The authors are both treating the model's training priors as the adversary. The design move is that framing, not the surface features. Speaker-heavy slide — rehearse.
03 · Move 1 · Name the anti-pattern03 / 16

Vague guidance loses to strong priors. Name the specific wrong thing.

impeccable

Instead of “use good fonts”:

“DO NOT use Inter, DM Sans, Plus Jakarta, Instrument Serif, Fraunces, Space Grotesk…”

superpowers

Instead of “consider checking the skill”:

“1% chance it applies means you MUST check.”

"Use good fonts" activates nothing — the model's prior for "good font" is Inter, because that's what the training data optimized for. "Do not use Inter" forces a real decision. Same structural move in a non-visual skill: deck-architect (the skill that built this deck) ships a forbidden-phrase list — "leverage," "unlock," "seamlessly" — with concrete replacements. The domain does not matter. The move is always: name the specific wrong thing, name the replacement.
04 · Move 2 · Write the rebuttal first04 / 16

Write the rebuttal before the model writes the rationalization.

What the model is about to think Rebuttal that fires first
“I just need a little more context first.” Check the skill before you ask for clarification.
“This case is genuinely different.” Every case feels different under pressure. Check anyway.
“The user seems to want me to skip this.” Skill priority list beats inferred user intent.
“I'll do it next turn.” Next turn does not exist. Do it now or name the skip.
The rationalizations the model reaches for when it wants to skip a step are remarkably uniform across sessions and across users. Observing yours once and writing the rebuttal inline is the single highest-leverage authoring move in this whole talk. This is why Superpowers has the Red Flags table and why deck-architect has rationalizations.md. The excerpt here is four rows; the full Superpowers table is twelve. Sizing is in Q&A — acknowledge that SKILL.md grows when you do this, then point at the tradeoff slide two clicks later.
05 · Move 3 · Ship a check05 / 16

Ship a check that runs without Claude. Trust is a load-bearing feature.

impeccable's standalone auditor

Node CLI · CI-runnable · 24 rules

Scans HTML and CSS for the exact patterns the skill bans. Zero AI runtime. Anyone can run it. If the skill fails, the CLI tells you where.

superpowers' subagent pressure-test

Subagent · from a clean slate · verifies trigger

A fresh agent runs the skill cold and reports whether it fired when it should have. Instructions drift under model variance; programmatic checks do not.

This is the move that separates a piece of prose from a system. Your skill probably has no external verification today. Mejba's controlled test picks up on this implicitly: the measured 14% token reduction came from skills with teeth, not skills with gentle suggestions. The Impeccable CLI is also a trust signal for installers — they can verify the skill works before adopting it. That's a distribution advantage, not just a correctness one.
06 · Move 4 · Decompose by failure mode06 / 16

Decompose by failure mode, not by topic.

By topic

One “design skill” that says “do design well.”

Too broad to trigger reliably. Fires on every frontend task and says nothing specific once it does.

One “engineering skill” that “enforces quality.”

Same problem, different domain.

By failure mode

/audit for missing accessibility
/distill for over-elaboration
/colorize for palette reflex
/quieter for over-animation

Each targets one specific failure the model makes. Triggers fire cleanly.

superpowers: brainstorming, writing-plans, subagent-driven-development, requesting-code-review

Same pattern at workflow scale.

Topic-decomposition creates skills too broad to trigger. Failure-mode decomposition creates skills that fire exactly when they are needed. Pragmatic threshold for the audience: start with one failure mode per skill; split only after you observe the same skill firing for genuinely different failures in your actual usage. If the room is early in their skill-authoring journey, slow here and give a second example — "the model skips writing a plan" versus "the model writes a plan that's too abstract" are different failures, not one topic.
07 · The multiplier07 / 16

A chain of enforcement skills beats any single hero skill.

Superpowers' handoff chain is why reviewers describe it as transformative, not additive.

using-superpowers → brainstorming → writing-plans → subagent-driven-development → executing-plans → requesting-code-review → finishing-a-development-branch

Mejba's controlled test — 12 sessions, 14% token reduction overall, gap concentrated on complex tasks, negligible on simple ones.

Evan Schwartz's review specifically highlights the chain effect — no individual skill was the thing; the sequence was. Mejba's controlled data backs it: on simple tasks, Superpowers produces no measurable improvement; on complex multi-step tasks where the full chain runs end-to-end, it does. The lesson for skill authors is that the multiplier is in composition, not any one skill. If you own two or three enforcement skills, designing the handoffs between them is where the next 2x is hiding.
08 · What you give up08 / 16

What you give up: bigger files, sharper edges, real authoring effort.

  1. SKILL.md roughly doubles in size.Rationalization tables and ban lists cost context budget every session. The smallest usable version is one banned phrase and one rebuttal — still worth it.
  2. Opinionated skills fight user instinct on edge cases.The user-wins priority rule only covers the obvious ones. You will see friction from people who wanted a looser suggestion.
  3. You cannot ban a pattern for a domain you have not lived in.The authoring bar is real expertise, not prose skill. Thin expertise produces bans that feel arbitrary and get ignored.
Name the "sounds heavy" instinct directly — the audience will think it before you get there. Counter: the smallest version of this is still worth doing. One banned phrase, one rebuttal, one concrete check. Twenty-minute authoring session. The payoff is not in the size of the intervention, it is in the fact that it fires.
09 · Rollback in 72 hours09 / 16

If this backfires, detect it in 72 hours — not a week.

Rollback path

  • AKeep the prior SKILL.md as SKILL.md.prev in the same folder before you ship the change.
  • BLog invocation count for the first 72 hours — a single tally per session is enough.
  • CIf invocations drop more than 30% vs. baseline, triggers regressed. Restore .prev, diagnose, retry.

When not to do this

  • Skills with fewer than five real invocations of evidence — you'll over-fit to noise.
  • Bans without a specific replacement behaviour.
  • Anywhere enforcement would fight a user's explicit instruction. User wins.
Anticipate the "I will not notice for a week" objection and answer it with the 72-hour invocation-count check. It is cheap, it survives being forgotten (you either see the number drop or you do not), and it prevents the week-of-silent-regression scenario. The three "when not to" rules are your permission slip to not apply every move to every skill — the audience needs that release valve or they will dismiss the whole deck as over-engineering.
10 · The action10 / 16

The best skills are not instructions for Claude. They are enforcement systems tuned to Claude's specific failure modes.

Pick
One skill you already own.
Apply
Move 1 + Move 4.
Name the anti-pattern. Decompose by failure mode.
Ship
Before Friday. Check invocation count at 72h.
The deck's job ends when the audience commits. Do not leave this slide until at least one person has named the skill they are going to modify. Move 1 + Move 4 is the "if you can only do two" recommendation — highest reliability return for the least authoring effort. Someone will ask about questions — answer verbally, keep this slide up during Q&A. Do not replace it with a "thanks" slide.

/critiqueReviewer voice; strongest objection first.
/polishTighten spacing rhythm and text sizing.

/bolderPush aesthetic intensity one notch past comfort.

/quieterRemove decorative motion and shadow.
/shapeSilhouette and negative space pass.
/overdriveMax intensity — used rarely.
/verifyRe-run audit after changes.

Each command targets one specific failure the model makes. The surface looks wide, but the decomposition is the skill's actual backbone — a single “design” skill doing all eighteen jobs would trigger on everything and commit to nothing.

This is the long-form answer to "what does each command do." Don't walk through all eighteen on stage — point at the pattern. The commands that matter most for a first-time author to study are /audit (proof of standalone verification), /distill (the anti-elaboration failure mode), and /colorize (explicit-ban replacement).

B3 · evidence · Mejba14 / 16

The honest version of the 14% number.

Simple tasks ~0%
Medium tasks -8%
Complex tasks -22%
Multi-step -28%

12 paired sessions, single-author evaluation, task-selection bias not controlled for. The 14% headline is the unweighted average; the real distribution is heavy-tailed. On simple tasks, no measurable benefit.

This is the slide that buys the deck's credibility. Don't hide the caveats. Single-author, small n, selection bias all named. The claim is useful — not definitive — and the honesty about that is what makes the rest of the deck believable. If the room pushes for rigor, this is the right bar to meet.
B4 · why the tone15 / 16

The “you MUST” language is testing-derived, not stylistic.

Authority, commitment, scarcity — Cialdini's three levers that reliably shift behaviour, applied to a model that will argue its way out of a soft instruction but complies with a hard one. The capital letters are load-bearing. obra — fsck.com, Oct 2025 (paraphrased)

The uppercase tags (“EXTREMELY-IMPORTANT”) look aesthetic but were arrived at by A/B-testing compliance rates. Soft versions of the same instructions produced measurably worse adherence. Treat tone decisions as testable.

Answer to the "isn't the authoritarian tone off-putting?" objection. The tone is a feature, not a bug. The Cialdini framing is also useful for authors who don't want to sound like drill sergeants: you can be warm in prose and firm in instructions, and the firmness is specifically what gets obeyed. Soft enforcement is indistinguishable from suggestion.
B5 · the CLI, inside16 / 16

The Impeccable CLI is smaller than it looks.

Reads the output HTML/CSS. Applies roughly 24 deterministic checks — font present in the approved list, contrast ratios above threshold, padding rhythm on the 4pt scale, heading-level monotonicity. No AI runtime at execution time; just a Node script. CI-runnable.

The architectural move is: any skill can ship with a companion verifier. The verifier does not need to understand intent — it only needs to encode the bans.

$ impeccable audit build/index.html
  ok: no reflex fonts
  ok: no gradient text
  ok: heading monotonicity
FAIL: border-left 4px on .callout
FAIL: card nested inside card (.panel > .panel)
FAIL  build/index.html — 2 check(s) failed
The companion lint for deck-architect is the same architectural move — regex checks over the rendered HTML, no AI needed to run. The payoff is asymmetric: a few hundred lines of deterministic Node buys you verification that the skill's own instructions are being followed. If someone asks "can I really do this for my own skill" — yes, and the effort is one afternoon.
