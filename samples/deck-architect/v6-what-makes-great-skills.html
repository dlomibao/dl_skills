02 · the reframe02 / 17

Both skills are enforcement systems dressed as capability skills.

What people install them for

  • Better typography
  • A TDD workflow
  • Clean design output
  • A checklist you can hand Claude

What they actually do

  • Forbid the eleven fonts Claude reaches for
  • Pre-empt the fourteen excuses Claude uses to skip TDD
  • Reject the design patterns before generation
  • Encode the rules so a Node script can enforce them
This is the STAR line. Quote pbakaus on generic-template convergence; quote obra on "if you have a skill to do something, you must use it." Both authors explicitly name the model's own defaults as the adversary. Surface features are downstream of that framing. If the audience remembers one line from this talk, it is this reframe.

04 · move 02 · rebut the excuse04 / 17

Rebut the rationalization before the model writes it.

What the model is about to think The rebuttal that fires first
“This case is special.” No exceptions. Tests still run.
“The user is in a hurry.” Speed comes from skipping review, not skipping tests.
“This is a trivial change.” Trivial changes are where silent regressions hide.
“I already understand the problem.” Write the failing test and confirm your understanding.
“One-percent risk is acceptable.” One-percent means you MUST check.

Excerpt of the superpowers Red Flags table. The pattern is the move; the exact list is domain-specific to the skill.

The excuses Claude reaches for under time pressure are uniform across sessions. Observe the ones your own skill provokes once, then write the rebuttal inline. This is the move that separates usable from installed — it is why superpowers feels different from "a good prompt." The rationalization is named before it runs. Ask the room: what excuse does your last-authored skill fail on most? Whoever answers first has their Friday task.
05 · where skills sit05 / 17

Where these two sit, compared to what power-users typically ship.

Most power-user skills live in the broad-but-soft quadrant — they cover a lot of surface with polite guidance. The shipping move is not to redraw the skill; it is to add teeth. A narrow-but-sharp skill beats a broad-but-soft one every time, because the narrow one actually fires. This quadrant is a thinking tool, not a ranking — grading my own two skills on it is itself a bias. Invite the room to plot one of their own during Q&A.

07 · move 03 · the mechanism07 / 17

Ship a check that runs without Claude.

impeccable audit — a Node script, ~24 deterministic checks

$ impeccable audit build/index.html
  ok: no reflex fonts              # font-family vs reject list
  ok: no gradient text             # impeccable BAN 2
  ok: heading monotonicity         # h1 > h2 > h3 size order
FAIL: border-left 4px on .callout # impeccable BAN 1
FAIL: card nested inside card    # .panel > .panel

FAIL  build/index.html — 2 check(s) failed

Your skill needs a check that does not require Claude to grade Claude. The verifier does not need to understand intent — only to encode the bans.

A few hundred lines of deterministic code buys external verification that the skill's instructions actually held in output.

lint-deck.js is the same pattern applied to this deck — regex checks over the rendered HTML, no model in the loop. Thirty lines of work, permanent reliability dividend.

The point is the pattern, not the command list. A Node script with regex checks is all a verifier needs. Superpowers ships the same architectural move at a different layer — its subagent pressure-test is a fresh-session verifier that proves the skill fires from a clean slate, with no author bias. The deck in front of the room was linted with a script on the same architectural pattern — regex checks over the rendered HTML, no model at runtime. The payoff is asymmetric: effort to build is one afternoon, reliability buy is permanent.
08 · move 04 · split by failure08 / 17

Decompose by failure mode. Then chain the skills.

Topic-decomposition ("a design skill," "a testing skill") creates surfaces too broad to fire reliably. Failure-mode decomposition creates skills that fire exactly when needed. Once each skill is sharp enough to trigger on its own, chain them. Schwartz's review names the chain effect explicitly — no single skill does the work. The fourteen-percent token reduction two slides back was concentrated on exactly the complex multi-step tasks where this chain runs end-to-end. Pragmatic threshold: one failure mode per skill until the same skill fires for genuinely different failures.
09 · what you give up09 / 17

What you give up: longer files, sharper edges, real authoring time.

  1. SKILL.md roughly doubles. A ban list and a rebuttal table are real tokens. A twenty-line skill becomes forty lines before you have measured anything.
  2. Opinionated skills fight the user on edges. Enforcement cuts both ways — sometimes the user was right. You need an override path, and you need to actually use it when the override is correct.
  3. The first pass is weak, and you have to live with it. You cannot write a ban list for a domain you have not lived in. The skill sharpens only with invocation data; budget for version two.
The smallest useful version is one banned token plus one rebutted excuse. Twenty authoring minutes, not a weekend. Name the "sounds heavy" instinct directly — the audience is thinking it before you say it. Call out one skill you would not apply these moves to this quarter and why: if the skill has fewer than five real invocations, you are guessing at the ban list and will ban things you later need.
10 · rollback10 / 17

If this backfires, catch it in 72 hours — not next sprint.

The 72-hour check

  • AKeep the prior SKILL.md as SKILL.md.prev beside the new one. One-line diff is your rollback path.
  • BLog invocation count for 72 hours after the change. A terminal ring-buffer of fired-skill names is enough.
  • CIf invocations drop by more than 30% against the trailing week, triggering regressed — restore, diagnose, retry.

When not to do this

  • No enforcement on skills with fewer than five real invocations — you are guessing.
  • No ban without a specific replacement — half a move is worse than no move.
  • If enforcement consistently fights user intent, the user wins. Every time.
Anticipate the "I will not notice regressions for a week" objection head-on. The 72-hour check is cheap, survives being forgotten, and catches the failure mode of a ban list with no replacement. The 30% drop threshold is a practitioner heuristic, not a controlled number — if someone pushes on it, flag that and be honest. The point is the existence of a pre-committed threshold, not its exact value. Rollback lives in main flow because this deck asks for a change to a working artefact.
11 · pick, forbid, check11 / 17
A skill earns its keep by forbidding the model's defaults — not by describing behaviours you wish it had.
Pick.Forbid.Check.
PickA skill you already own.
ForbidOne specific token — start with Move 01.
CheckInvocation count, 72 hours, 30% threshold.
The deck succeeds when the audience names a skill aloud. Ask for one out loud before the room moves on — the public commitment is what makes Friday happen. "Pick, Forbid, Check" is a memory aid: Pick a skill, Forbid a specific token (Move 01), Check triggering at 72 hours. The middle verb is deliberately the cover word — the close and the cover should land on the same sound. If the room is early-career, offer to help someone in Q&A pick which skill and which token. B4 · why the tone16 / 17

The “you MUST” language is testing-derived, not stylistic.

Authority, commitment, scarcity — Cialdini's three levers that reliably shift behaviour, applied to a model that will argue its way out of a soft instruction but comply with a hard one. The capital letters are load-bearing. obra — fsck.com, late 2025 (paraphrased)

The uppercase tags (“EXTREMELY-IMPORTANT”) look aesthetic but were arrived at by measuring compliance. Soft versions produced measurably worse adherence. Treat tone decisions as testable.

Answer to the "isn't the authoritarian tone off-putting?" objection. The tone is a feature, not a bug. You can be warm in prose and firm in instructions — the firmness is specifically what gets obeyed. Soft enforcement is indistinguishable from suggestion, which is why it fails silently.
B5 · the CLI inside17 / 17

How impeccable's auditor is shaped.

Reads rendered HTML and CSS, applies roughly 24 deterministic checks — font family against a reject list, gradient-text detection, border-left width ban, contrast ratios, heading monotonicity, padding rhythm on a 4pt scale. No AI runtime at execution time; a Node script. CI-runnable.

The architectural move: any skill can ship with a companion verifier. The verifier does not need to understand intent — it only needs to encode the bans. A few hundred lines of deterministic code buys external verification that the skill's instructions are being followed.

$ impeccable audit build/index.html
  ok: no reflex fonts
  ok: no gradient text
  ok: heading monotonicity
FAIL: border-left 4px on .callout
FAIL: card nested inside card (.panel > .panel)
FAIL  build/index.html — 2 check(s) failed
This deck was itself linted by a companion script on the same architectural pattern — regex checks over the rendered HTML, no model in the loop. The payoff is asymmetric: the effort to build is one afternoon; the reliability buy is permanent. If someone asks "can I really do this for my own skill" — yes, and the smallest useful version is a single check for your single most common failure.
